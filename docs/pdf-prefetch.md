# Slipstream: predictive PDF loading

Slipstream is the shared viewer, predictive loading, and cache layer behind both extension engines and the standalone [Spomenar site](spomenar.md). They use the same controller, [pdf-prefetch.ts](../views/pdf-viewer/src/common/pdf-prefetch.ts), with PDF.js 5.1.91. Each passes its `PDFViewer` to `installPdfPrefetch` once during startup. Document replacement resets the controller through the page lifecycle events. [scroll-prefetch.ts](../views/pdf-viewer/src/common/scroll-prefetch.ts) owns the motion estimator and device cache policies.

## Scheduling and cache layers

The estimator follows CoS's `TimelineScrollDynamics`: react immediately to faster motion or a slower page, then decay the estimates gradually. Wheel events predict motion before the next scroll frame; the controller avoids counting that movement twice. Scroll events cover keyboard navigation and scrollbar movement. The selected policy's gesture gap clears velocity and acceleration, while the document's loading-time estimate remains available. The default is 250 ms; the estimator and controller settlement timer receive the same value. Acceleration is diagnostic; velocity, the latest displacement, and measured page latency determine the preload distance.

[Render timing](../views/pdf-viewer/src/common/pdf-render-timing.ts) excludes measurements made while the browser withholds rendering frames. While measurements are active, one probe requests a frame and starts a one-second timer. If the timer arrives within 100 ms of its deadline but the frame has not arrived, the active measurements are discarded. A late timer can reflect substantial foreground work, so that delay remains part of a valid render measurement. Cancellation, invalidation and disposal release the probe; it stops when the last measurement finishes.

The desired distance starts at two viewports, with a 480 px minimum. It grows with speed and page latency, up to twelve viewports or 12,000 px, whichever is smaller, while preserving the base distance for large viewports. Direction changes immediately on reversal.

The controller uses five cache layers:

1. The extension keeps verified content-addressed pieces and incremental range blobs on disk, under one budget across all builds.
2. PDF.js stores received bytes as sparse chunks within its active document.
3. Prepared PDF pages retain PDF.js display operators and decoded resources.
4. Small raster previews cover pages while full-resolution rendering catches up. Mobile retains nearby previews at up to 512 px and reduces older detached previews to 192 px before eviction.
5. PDF.js owns the full-resolution page canvases and their rendering queue.

The persistent [disk cache](../src/core/pdfDiskCache.ts) accepts complete GET requests to `/content/<contentId>/<SHA-256>` when the response bytes match the hash, and verified `output.pdf` ranges with stable validators. A build is represented by byte-interval metadata and received blobs. The host fills missing intervals gradually while every visible reader is idle. The configured `pieceCacheSizeMB` budget, 4096 MiB by default, includes old and new builds, reusable content pieces, range blobs, metadata, and bytes reserved for current writes. A new build does not create a full-size file. `0` disables disk caching and background fill.

The cache owns its operation queue and short writer leases. Network transfers run outside the writer lease and foreground read queue. Exact-build exports use the same cache admission and cancellation machinery.

Each cached single or multipart response captures one manifest, validator, segment list and complete set of ordered read plans before reading bytes. A concurrent host can publish a new representation without mixing it into that response. If any captured immutable blob disappears, the entire cache hit is rejected. `If-Range` requests use the origin path so its [HTTP conditional-range rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) decide whether the range applies; a whole-document `200` is canceled before its body is read.

The [pinned PDF.js patch](../views/pdf-viewer/vendor/pdfjs-5.1.91-dist.patch) adds `rangeCacheBytes`, `getRangeCacheStats()` and `trimRangeCache()` to the same runtime used by both engines and the website. Reading a range checks that each chunk is resident, including the initial progressive prefix. Old chunks can be fetched again after eviction. Active parsing, asynchronous page work, rendering tasks and detached image decodes hold the bytes they may still need. Once those operations finish, the worker trims its LRU to the selected budget.

The worker budget is its idle residency target. One active PDF stream can exceed it temporarily, so the shared controller also stops new cold-page work while the byte cache is over budget. A completed preparation keeps its admission slot until the worker has answered a trim request. Running and fully prepared native pages can continue. A 250 ms memory check runs only while work or memory pressure remains; it operates even with Motion Lab closed, and stops when the document is hidden or disposed. This lets ongoing work finish and gives the worker a chance to release bytes during continuous scrolling.

An image acquires its range hold only after the decode queue admits it. The hold covers image construction, asynchronous decoding and missing-range retries, then releases before the worker trims between queue slots. Queued images can refetch evicted source bytes when admitted. This prevents a long image queue from holding the complete range cache above its idle target.

Preparation uses small `pdfPage.render()` calls with the display intent shared by native rendering. At most three cold pages on desktop, or two on mobile, are admitted across speculative previews and the auxiliary renders that track native resource preparation. A new cold native render starts only after its small auxiliary render is running. That auxiliary render holds its slot until preparation actually completes. Completed native renders and previews mark resources warm; PDF.js clearing the same page proxy's rendering-intent map revokes that status.

Native visible pages and holes in spread layouts retain their rendering priority. An uncovered visible page blocks further offscreen admission. When scrolling makes an already-started preview obsolete, it becomes `retiring` and finishes while holding its slot. This prevents repeated canvas cancellation from launching unbounded worker decoding. Obsolete `getPage` requests whose render has not started are discarded. Document replacement, layout changes, hidden documents, and disposal still cancel work; completion checks reject stale results.

During mobile motion, a visible page whose compatible nonempty preview is attached to the current page waits for the existing gesture-settle event before starting cold native preparation. Warm and already-running work continues. Missing, detached or invalid previews retain immediate native fallback. This keeps fast traversal from decoding each passing page after the preview already supplies its displayed pixels.

Full-resolution lookahead stays within two viewports. Counting visible pages and spread holes in that window avoids repeatedly evicting and redrawing pages through PDF.js's default ten-view buffer. Rotation, theme, and optional-content changes invalidate saved previews; zoom can reuse and resize them. Disposing the controller removes listeners and restores the queue methods.

On both device policies, a retained distant preview is sufficient coverage without keeping decoded photo resources. Finished native canvases release their operator lists and every decoded resolution tier, including when the canvas is still visible. The explicit `releaseRenderedResources` policy is separate from mobile's `pruneOffscreen` canvas policy: desktop retains its larger native-canvas window. PDF.js defers resource cleanup until every active render and its operator list have finished. The native canvas and retained preview remain ready, and neither starts another decode merely to warm resources again. A later zoom requests fresh rendering at the new scale.

The [graduated preview cache](../views/pdf-viewer/src/common/pdf-preview-cache.ts) protects visible, attached, and prepared rasters, reduces the oldest unprotected entries first, then evicts only if needed. A returning finished native canvas upgrades its smaller trail preview with `drawImage`, without decoding the PDF again. Replacing an attached raster publishes its new node before releasing the previous bitmap. Failed admissions and canvas-allocation failures wait for the visible-page plan to change instead of retrying on every refresh.

### Raster and page coordinates

The shared [raster projection module](../views/pdf-viewer/src/common/pdf-raster-projection.ts) maps normalized logical page coordinates to backing pixels and to displayed CSS pixels. It keeps the full logical content rectangle separate from the visible page clip. PDF.js rounds its canvas backing and CSS dimensions while retaining the unrounded render viewport; using the rounded page box as the full logical page would shift and scale previews and photograph masks. The observed 50% Antigravity view, for example, has a 332.599 × 472.441 CSS-pixel logical page inside a 330 × 470 clip, with a 396 × 564 native backing.

Each preview retains its projection with its canvas. Atlas images cover the complete normalized page. Independently rendered previews retain their unrounded viewport within the ceil-sized backing. Native copies retain the original viewport and actual output scale captured at the main `pagerender` event, including any clipped edge. Cache resizing scales that mapping independently on both axes. CSS-only rotation changes the logical basis of the retained pixels, so a clipped edge moves to the correct side without another full-page bitmap. CSS-only zoom derives displayed content from that saved mapping and the current native canvas box.

A main draw can allocate its native canvas before attaching it. Until that canvas has a display box, the ready preview uses the current logical viewport and page clip. The provisional geometry remains uncached so the next update can measure the attached canvas, even when the viewport has not changed.

Photo crops read outward from the floor of each source start to the ceiling of each source end. The bounded cargo canvas applies the exact logical transform, so the extra sampled edge pixels do not stretch the photograph or change its landing target during refinement. The source cover rounds outward on the displayed raster's pixel grid, adds one physical display pixel to cover fractional compositor edges, and clips to the visible page. That margin is `1 / (devicePixelRatio * visualViewport.scale)` CSS pixels, with a scale of one when the visual viewport is unavailable. Preview clipping, source sampling and cover placement use the same projection helpers in both extension engines and Spomenar.

### Display-sized image decoding

`pdfDocumentCacheOptions()` supplies the same document options to the extension's two engines and Spomenar. Both device policies enable adaptive display-image decoding. Mobile admits one image job per document; desktop admits two while retaining its three cold-page preparation slots and larger raster budgets. These limits cover image construction as well as decoding: one admitted collage page can contain many large photographs. Printing requests original detail.

The display proxy derives image density from the page viewport and actual output transform. Auxiliary previews request the native canvas's density so they can prepare the same decoded resources. Resolution is part of the display-intent identity; a prepared higher-resolution intent can satisfy a smaller render, while a larger zoom requests new detail. Warm-resource records carry the same density and are rejected if the new zoom needs more pixels.

The worker composes each image's placement matrix, including nested Form matrices, and rounds the requested dimensions upward. Repeated image XObjects at different sizes have separate cache entries. Tiling patterns use a conservative page-sized bound when the placement cannot be determined. Adaptive intents avoid the original reference-only global image cache, which could otherwise reuse a smaller image at a larger zoom.

Plain, unmasked DeviceRGB JPEGs decode directly to their required bitmap dimensions through the browser's native decoder. Orientation, color conversion and alpha premultiplication options are explicit, and the existing PDF.js JPEG compatibility checks and EXIF removal remain in use. A decoder that returns the wrong dimensions has its bitmap closed. If the native path is unavailable, a fresh JPEG decoder produces scaled pixels; reusing the same compressed stream at a later zoom therefore cannot reuse an earlier small output buffer. Other image semantics keep the existing PDF.js decoding path.

Active image jobs validate their encoded source and mask ranges before construction, then retain those ranges until decoding completes. Incremental decoders therefore start with resident bytes even after their queued sources were evicted. Document termination rejects waiting jobs and closes late native bitmaps. Image statistics travel with the existing range-cache statistics request, so the feature adds no separate polling loop.

### Transfer admission

PDF.js can continue worker image and range requests after a render task is cancelled. Before admitting a page whose resources are cold, the controller also checks unfinished viewer fetches. On desktop it pauses new cold native renders and cold preview preparations when at least twelve fetches are pending, or when at least six are pending and the oldest has reached 1,500 ms. Mobile uses thresholds of six and three respectively. Existing running or paused native renders can continue or resume, and pages with fully warmed resources can render from those resources.

These are admission thresholds: one admitted page can request several images, so the number of pending fetches can exceed its threshold. `onFetchChange` schedules a coalesced refresh as requests finish, allowing waiting work to resume from observed completions. The cold-page limit also includes work still decoding after its transfers finish.

### Host response ownership

The shared [bridge response helper](../views/pdf-viewer/src/common/bridge-response.ts) consumes bytes that have already arrived in a private host message. It transfers the owned buffer into a native byte stream instead of copying it into `Response`, then reads that one complete chunk directly. Full-span chunks reuse their transferred backing buffer; sliced views get one exact-range copy so neighbouring bytes cannot escape. Transfer accounting runs before enqueue detaches the original buffer.

The build adapts exactly two response-consumption sites in the pinned Overleaf loader, and stops if their source no longer matches. Both extension engines use this path. The original HTTP responses used by Spomenar follow native `arrayBuffer()` consumption. Cloned, locked and consumed responses also keep native handling; [Fetch's body-clone operation](https://fetch.spec.whatwg.org/#concept-body-clone) replaces the original stream with a tee branch, so neither clone branch is marked for direct consumption. Final PDF range reassembly still owns a separate buffer for transfer to the worker, preserving chunks retained by the incremental loader.

### Budgets and thresholds

The authoritative values are selected by `pdfCachePolicy()` in [scroll-prefetch.ts](../views/pdf-viewer/src/common/scroll-prefetch.ts). Phones and tablets use the mobile policy, including iPads with desktop-mode user agents. A touchscreen desktop keeps the desktop policy. Callers can provide an explicit `cachePolicy` to the shared controller.

The policy separately owns sidecar browser decoding through `sidecarDecode.concurrency` and `sidecarDecode.maxInputEdgeScale`, a multiplier of the retained preview edge. `pdfSidecarDecodeOptions()` derives those consumer limits in the same module. Legacy custom policies without the optional setting retain the previous named-profile fallback. Sidecar decoding and PDF worker image jobs remain independent consumers with explicit budgets.

| Resource | Desktop | Mobile |
|---|---:|---:|
| Planned preparation window | 16 pages | 6 pages |
| Cold page preparations, including pending `getPage` and retiring jobs | 3 | 2 |
| Pending-fetch threshold for pausing cold work at any age | 12 | 6 |
| Pending-fetch threshold when the oldest reaches the age limit | 6 | 3 |
| Oldest-fetch age limit | 1,500 ms | 1,500 ms |
| Full-resolution targets, including visible pages and spread holes | 8 | 3 |
| Full-resolution canvas admission and cleanup target | 192 MiB | 48 MiB |
| Preview maximum dimension | 768 px | 512 px |
| Distant trail preview maximum dimension | No downsampling | 192 px |
| Retained preview raster storage | 64 MiB | 8 MiB |
| Retained preview count | 128 | 128 |
| Sparse worker byte-cache target | 128 MiB | 32 MiB |
| Concurrent adaptive image jobs | 2 | 1 |

Visible pages remain protected. Mobile destroys native canvases outside its current visible/render-ahead plan when their active preparation has finished, even when their total is below 48 MiB. It retains the graduated preview LRU for revisits and releases unneeded display resources. PDF.js also maintains decoded resources outside the raster byte counters.

## Early page previews

Both extension engines and Spomenar use the same [preview-source consumer](../views/pdf-viewer/src/common/pdf-preview-source.ts). The [Motion Lab postprocessor](motionlab-previews.md) prepares 192, 512, 768 and 1536-pixel page images with their intrinsic CropBox orientation and optional photograph placements. These small assets can cover a page while PDF.js prepares its original resources. The shared preview cache owns admitted canvases, so sidecars use the same retention and eviction budgets as previews rendered by PDF.js.

Every source is bound to the exact installed `PDFDocumentProxy`, document identity, byte length and page count. The extension uses its canonical cached-build key and an export receipt; Spomenar additionally matches the published digest against the PDF transport's observed size and HTTP validator. The host watches atomic manifest publication and announces changes to the correct webview generation. An absent or rejected sidecar leaves native rendering available. Idle viewers do not poll for another manifest.

The native Overleaf viewer can defer document installation through `startViewTransition`. Its [preview binding](../views/pdf-viewer/src/common/pdf-preview-binding.ts) waits for the actual installed proxy before attaching a preview source. Antigravity stores the host preview root as a `vscode-userdata` URI while local preview descriptors use `file:`. The webview resource permission converts that exact root to a file URI at the resource boundary.

The native [document manager](../views/pdf-viewer/src/overleaf/documents.ts) keeps the displayed document and its loading task alive while a candidate is validated. It waits for the real viewer setter and the wrapper's completion before announcing the new build, retiring the previous task and attaching the candidate's preview metadata. A cancelled delayed callback is rejected before it can assign either the viewer or the link service. The build's checked adaptation handles the transition's `updateCallbackDone` rejection, while the manager retains the candidate's success or failure outcome.

Range and inline replacements share one [temporary height owner](../views/pdf-viewer/src/common/document-height.ts) per viewer element. The hold starts at actual assignment and preserves the preceding page height until `pagesinit`. Abort or setter failure releases its listener and restores the previous style; a superseding hold releases the older owner first. The full PDF.js entry point announces the new build after `load` succeeds and closes a partially installed candidate if its viewer setter fails. Optional scene preparation can fail without preventing a ready document from opening.

The loader gives every uncovered visible page its smallest usable image before refining either half of a spread. At most two requests occupy the pipeline; cancelled requests retain their slots until cleanup finishes. Phone image decoding is serialized and capped at a 512-pixel longest edge. Desktop permits two decodes with an input edge of at most 1536 pixels, retaining its normal 768-pixel preview size. Encoded dimensions, declared byte counts and SHA-256 are checked before browser decoding; the decoded dimensions are checked again before publication. Hidden documents, replacements, incompatible themes or optional-content changes cancel the binding, and late bitmaps are closed.

## Document deliveries and diagnostics

The SVG robot button in every viewer header enables the document effect, which starts on. A page's first substantial visible encounter summons the fleet to carry real rendered fragments into place, including when prefetch has already prepared the page. The controller uses the finished native canvas or an available preview without starting another render for the effect. Offscreen prefetch completions do not start a delivery. A preview and its native replacement share one episode per page and document; revisiting, zooming or toggling a delivered page does not repeat it. The effect leaves text selection and document controls available.

During active scrolling, an otherwise usable page starts a delivery when its visible inner clip reaches the reading viewport's midpoint along the scroll axis, or when the page fits fully inside that axis. This postpones job selection from an incidental entering strip while allowing magnified pages that cover the middle and fully visible small pages away from it. The same rule applies in both scroll directions and horizontal layouts. The controller also recognizes a changed scroll position before the scroll listener runs. Once the existing scroll-settle event fires, a usable partial view can start immediately. Zoom and layout changes use the resulting view. These checks precede crop selection and allocation; PDF rendering and preview display continue on their existing schedules.

Before pixels arrive, a visible duplex can receive one advance crew for its actual `.spread` membership. The crew enters and coordinates for a finite interval, then parks without scheduling animation frames. A real preparation-state change can trigger one further gesture. Staging reserves no cargo and does not mark a page as delivered. Once pixels arrive, the delivery reuses the staged actors and their positions. Hidden, removed, failed or replaced work releases those reservations; reduced-motion mode shows static status.

### Photo arrivals and refinement

When matching placement metadata is available, couriers select actual image rectangles from the rendered page pixels and deposit them at those images' real locations. Normalized coordinates follow the page's intrinsic rotation and the viewer's additional rotation. A selected rectangle must have at least 32 CSS pixels visible in each dimension. The crop preserves the PDF's clipping and colour treatment. Candidate selection deduplicates the exact clipped source-pixel rectangle, including placement aliases and sampled fallback crops whose centers clamp to the same rectangle.

Each admitted payload is one page-region job with one crop, arrival cover, deadline and attached crew. The shared page-space planner rejects positive-area overlap with existing jobs before allocating a raster or reserving actors. It compares the final logical crop, allowing touching edges independently of raster rounding and cover padding. Whole photographs, collages and portions are chosen in content-priority order before ground routes are considered. A cooperative enlargement passes the same region check; other crews receive distinct work. Failed construction leaves no claim. Distinct placements of the same image remain separate jobs, and refinement joins the existing job without changing its region. Retirement uses the same rule separately for each old page, so its claims cannot suppress an incoming document.

The [document presentation policy](../views/pdf-viewer/src/common/robot-document-policy.ts) chooses cargo from its displayed CSS footprint. The maximum edge is 400 CSS pixels on desktop or 256 in compact presentation, multiplied by the bounded page-size factor described below. At smaller page sizes, a dense collage can travel as one piece; an ordinary photograph travels whole; a magnified photograph uses portions anchored to a fixed grid on that photograph. Only visible cells are examined, with at most 12 candidates from 256 supplied placements. Viewport movement cannot slide a portion's boundaries. Payload snapshots identify the crop kind and its source image IDs; the admitted crop, helpers, identity and deadline remain fixed through sharper previews and native rendering. Revisiting or zooming does not replay a handled page.

Grouping is limited to 12 fully visible, nonoverlapping images whose bounding rectangle fits that cargo envelope and contains at least 90% image area. Neighbours must form aligned rows or columns: their gutter is at most 8 CSS pixels and 6% of the smaller image edge, and their alignment differs by at most 2 CSS pixels and 2%. Every member has at least an 8 CSS pixel edge. Wider caption-like bands and sparse arrangements stay separate. Preview resolution and DPR do not change this selection for the same displayed page geometry.

Admission places a paper-coloured cover over the selected destination rectangle, including sampled fallback fragments. Its footprint rounds outward on the displayed raster and adds one source pixel on each edge, covering the filtered or encoded fringe that grows when a coarse preview is magnified. The shared projection preserves raster rotation and clips this footprint to the available backing. It then adds one physical display pixel at the current DPR and pinch scale and clips the cover to the page's inner box. Cargo sampling, dimensions and the logical photo target stay unchanged.

The cover belongs to the page, so it follows scrolling and column translation without another bitmap allocation. An active payload owns its copied raster, cover, refinement underlay and cleaner until deposit or a real terminal cancellation. Ordinary wheel, pointer-down, touch-start and key input preserve that ownership while still cancelling replacement teardown and column motion. Deposit reveals the page's real pixels and releases the transported raster and pixel attachments together. The same deposit transition records success once when native refinement or a visibility refresh reaches the deadline before its queued paint.

The landed photograph keeps a fading shadow for the shared 200 ms settle interval. A transparent element draws only that shadow; the real page image stays fully opaque and the cargo bitmap is already released. The existing payload clock owns the fade, so delayed paints cannot extend it. Terminal cancellation removes the shadow immediately, and the normal finite return ends with no scheduled frames.

Terminal release cannot recreate copied pixels or a cover through later refinement. The payload identity, helpers and original deadline remain available for the finite route and return, but photo-loaded poses and speech derive from the retained raster itself. An empty route cannot report a later photo deposit. An aircraft carrying another robot keeps that separate body-carrying role. Offscreen or removed pages, changed geometry or layout, hiding, disabling the effect, document replacement and disposal release the covers and active cargo.

PDF.js can remove page children during a native render reset. The current-document `pagerender` handler synchronously restores an existing arrival cover before refreshing work or attaching a saved preview. Restoration reuses the same cover and requires the same connected, visible page element, still-live cargo and the original pre-deposit deadline. A retired payload or replacement document cannot restore a cover. If a lost cover is not restored through that path, the next existing paint, refinement or visibility update retires the copied pixels; no extra timer or observer is needed.

New native pixels or a sharper retained preview can refine a still-active visible payload. Refinement requires the same page element, the same crop and a source with nondecreasing raster dimensions and at least one larger dimension. It preserves the payload and courier identities, displayed position, route and original deadline. Old and new rasters must fit the cargo budget together during replacement.

When spare actor and vehicle-backing capacity permit, [ASAP](../views/pdf-viewer/src/common/robot-cleaner-artwork.ts) wipes across the carried photograph. The coarse raster remains underneath while a directional clip progressively exposes the sharper pixels along the cleaner's pass. One cleaner can run at a time, at most once per payload, for 260 to 600 ms within that delivery's remaining lifetime. If a cleaner cannot be admitted, the sharper raster replaces the coarse one directly. Completion or cancellation releases the coarse bitmap, removes the clip and releases the cleaner's actor and backing storage. Refinement keeps the existing cargo-release deadline.

When the page base is visible, Navines preferentially takes a lower photograph or an ink-bearing lower fragment. It drives along the actual lower edge, raises that same raster on a visible mast, and deposits it at its original rectangle. A larger desktop crew can deliver an upper photograph cooperatively at the same time. Ground work uses the existing actor and cargo budgets; a base outside the viewport is not a forklift route. The payload snapshot reports `ground: true` and the `lift` stage, and cancellation removes both the mast and its single cargo raster.

### Scene limits and scheduling

[The document robot module](../views/pdf-viewer/src/common/pdf-document-robots.ts) varies the vehicles, entry sides, paths and ink-bearing fragment targets. It copies small fragments synchronously and never retains the source page canvas. The shared device policy keeps phones, tablets and narrow desktop panes at four couriers, 512 KiB of cargo and 200 KiB of vehicle backing storage. A desktop reading area with compensated available dimensions of at least 700 × 480 uses six to twelve couriers under a 3 MiB cargo limit and 24 MiB vehicle-backing limit. Its actor count still follows the raw CSS area. Vehicle artwork is redrawn for the actual displayed scale and pixel density, with backing resolution capped at DPR 3.

Actor limits count physical bodies. Without a Lab dispatch port, a new body can share a structural vehicle type with another active body; candidate selection prefers suitable unused types before reusing one. Each admitted body has its own identity, sprite and resource accounting. Borrowed Lab actors retain exclusive reservations until their owners release them.

[Screen sizing](../views/pdf-viewer/src/common/robot-screen-scale.ts) applies a CSS scale of `1 / sqrt(DPR)` to robot bodies, using an effective DPR between 0.5 and 4. This gives a fixed base sprite partial density scaling: its physical pixel size grows with the square root of DPR. Available dimensions divide the CSS viewport dimensions by that factor for desktop eligibility. The existing CSS-derived base size receives the factor once. Device classification and actor, cargo and backing-store limits remain separate from that presentation calculation.

Document bodies also receive `clamp((pageWidth * pageHeight / (640 * 900)) ** 0.25, 0.8, 1.35)`, using the actual CSS content extent of their page. This modest square-root response to page magnification is unchanged by a quarter-turn. It applies to delivery, advance, retirement, cleaner and column actors before the screen compensation, without a second pinch multiplier. A column actor captures the current visible page's numeric extent on admission; a spread's union does not enlarge it, and same-leg contact updates retain its scale. Lab dispatch positions and their departure scale remain independent. Vehicle and cleaner canvases use their admitted display scale and capped DPR under the existing joint byte limits, so a dense compact display can admit fewer sharp actors. Caption text remains 12 CSS pixels.

Only visible page IDs wait for capacity; queued work retains no canvas. The first busy offer suspends admission until an active delivery releases capacity. Pages deferred for visible area or entry timing retry when the view changes or the existing scroll-settle event schedules its refresh. A failed physical crop copy leaves the page unhandled and preserves its canonical decision for a later offer. Deferred work stays asleep between these events. Per-document handled history lives in the renderer and resets only for a replacement document. The pointer-transparent layer follows current page geometry and clips to the visible reading area, keeping the toolbar clear. Finished deliveries stop requesting animation frames; hidden or removed pages, layout invalidation, disabling, document replacement and disposal release active cargo. Reduced-motion mode cancels moving cargo, and a blocked visible offer can resume when that preference is disabled again.

The transit layer lives inside the existing PDF scroll container, so the browser carries couriers, cargo and parked crews with the document between scripted paints. Its zero-size origin uses layout and size containment with visible ink overflow; extreme sprite coordinates therefore cannot enlarge PDF scrollbars. PDF.js page offset parents remain unchanged. Direct work updates and animation callbacks share one finite 30 Hz gate that retains fractional frame time. A parked status or geometry change receives a deferred paint, then returns to zero animation callbacks; reduced-motion status remains immediate. Page/dispatch geometry is read before sprite styles are written.

The lab stays fixed under `document.body`, preserving its control and wheel-event ancestry. Shared styles move the page-content stacking boundary to the inner `.pdfViewer` with `isolation: isolate`, leaving page positioning intact. This lets document couriers pass above the lab while keeping page annotations below the viewer's toolbar and sidebar.

One scene-node initializer supplies absolute origin, hidden initial state, noninteractive styling and decorative accessibility attributes before courier canvases, labels and masts attach. Each becomes visible only after its first position is written. Forklift mast, fork and cargo attachment coordinates belong to the shared procedural artwork definition in [prefetch-robots.ts](../views/pdf-viewer/src/common/prefetch-robots.ts); the document renderer derives display geometry from its documented artwork scale and rounding rule. Route timing and page placement remain renderer policy.

### Transport

The fleet shares its physical descriptions in [robot-structure.ts](../views/pdf-viewer/src/common/robot-structure.ts). Relative mass, chassis, traction, lift mechanism and attachments determine carrying, lifting and towing support. The same mass contributes to ground bearing and traction and becomes part of an aircraft's load when it carries that robot. Personality describes teamwork, independence, emergency boldness, reverse aversion and affinity for a carrier. The [operation model](../views/pdf-viewer/src/common/robot-operations.ts) uses those properties for delivery, removal and rescue; VIV and EKO-KOMVOZ participate through their own structural descriptions.

Every photograph, collage, image portion and mixed or text fragment receives a workload from its admitted CSS dimensions: `max(width * height / (240 * 180), max(width, height) / 320)`. This relative scene load prefers one, two or three helpers as it crosses whole-unit thresholds, with the preferred crew capped at three. The actual load continues growing beyond three units, so the selected members must still supply enough support. Raster quality and DPR leave the admitted workload unchanged. A substantial piece normally travels with a pair, and the largest pieces prefer three members.

Page admission sums the preferred crews of its bounded set of candidate jobs before applying the shared actor limits. Its fragment limit separately bounds the number of jobs. Thus distinct heavy photographs can each receive their required team while every actual helper and copied raster remains within the physical budgets.

The [cargo adapter](../views/pdf-viewer/src/common/robot-cargo-operations.ts) describes who supports each load during each phase. A formation shares its photograph. A handoff charges the incoming and outgoing members during their respective carrying intervals. During an airlift, the ground robot supports the photograph while the aircraft lifts that robot and its photograph together. A forklift supports and raises its cargo concurrently. Assessment includes the required attachment, each member's condition, existing commitments and the reserve consumed by simultaneous mechanisms. Future load changes are included when a helper accepts another activity, including a photograph it will receive partway through the rescue.

The shared planner distinguishes three ways to accept work:

- A normal crew meets the preferred handling size and every phase's support requirement.
- A qualified smaller crew can volunteer. At the default personality values, the decision has a one-in-six chance; a sufficiently capable large robot can therefore occasionally carry a heavy piece alone.
- An overstrained crew can make a rare “Hiyaaaa!” attempt. Shortage of a qualified crew increases its willingness, and a smaller opportunity motive permits occasional bravado when qualified alternatives exist. Both motives decrease with strain and use the participants' personality traits.

Once an extraordinary attempt is committed, fulfillment has a 50% probability across delivery, removal and relocation. Strain determines partial progress, the chance of a clean triumph, and the resulting strain, smoke or disabled pose. The three outcome families are valiant failure, expensive success and clean triumph. Normal qualified work and qualified volunteers complete normally. All outcomes use the existing finite work, aftermath and recovery intervals.

One canonical job key combines the document generation, page, goal and exact logical crop. Its volunteer, willingness, fulfillment and aftermath draws remain stable across failed resource admission and a later change of available crew. The renderer retains at most 512 such decision records and clears them when the document resets or the renderer is disposed. Assessment can consider the newly available members while keeping those same draws.

Each payload owns one cargo crop, route, clock and attached crew. Admission prepares the selected couriers, checks their actual support, reserves their resources and copies the crop before publishing the job. A staged robot keeps its existing body, artwork and ownership until the complete transfer succeeds. Failed proposals return newly acquired resources once and leave staged alternatives available. Every committed helper counts against the actor and vehicle-backing limits, and a fulfilled deposit increments the fragment counter once. A partial attempt releases its cargo without recording a successful deposit. Refinement preserves the admitted workload, members, assessment, decision, outcome and original deadline.

The UAV-UGV sequence draws on the complementary roles in [Arbanas et al., *Decentralized planning and control for UAV-UGV cooperative teams* (2018)](https://doi.org/10.1007/s10514-018-9712-y). The aerial vehicle approaches with the fragment, meets a ground vehicle, pauses for a visible handoff and landing, then rides or accompanies the ground carrier to the deposit. The shared clock makes that order explicit. Crews return individually to their actual lab docks when their route permits, or leave through the viewport edge. The snapshot exposes payload IDs, helper IDs, mode, stage, progress and carrier so these transitions can be inspected.

The [airlift route](../views/pdf-viewer/src/common/robot-cargo-routes.ts) keeps the ground robot with its same photograph while an eligible aircraft helps it across a steep leg. The sequence is drive, recruit, rendezvous, lift, carry, set-down and final drive, all on the existing delivery clock. The route supplies positions for both bodies and the one cargo owner; a sling appears during the carried phase. Admission can reuse an eligible staged ground robot and assesses the actual selected aircraft against the complete load. Return can use the same route when reaching the ground dock requires air transport. A partial handoff or airlift starts recovery from each participant's achieved position and finishes within the original deadline.

L-UGV also prefers a lift when its next route reverses its last committed horizontal driving direction. Its gaze and hover reactions do not change that direction, and a newly admitted body has no invented prior heading. A lift requested for a turn keeps the exact pickup and set-down points and omits ground driving at both ends. The planner tries an already-owned capable aircraft, an uncommitted staged aircraft, then an available helper admitted through the ordinary reservation and backing limits. If no helper fits, L-UGV takes the valid ordinary route. The same decision applies once to its empty return, reusing its companion when available. Recruitment preserves the original deadline and cargo identity; promotion, failed artwork and terminal cancellation release the pair's sling and reservations together. Other shallow routes stay on the ground.

Ordinary ground approaches and departures follow straight paths with a vertical-to-horizontal slope no greater than 0.25. Side entry and exit points keep their chosen height when reachable and clamp it to that limit otherwise. A formation containing ground vehicles gathers at an actual ground member's launch when available, then carries its photograph along a shared shallow straight path. The ground member in a handoff approaches the rendezvous and completes the final leg along the same shallow line. Ordinary ground actors return to their current lab dock when that route is shallow enough; otherwise they use a side exit. The cargo, any coarse refinement underlay, mast and sling follow the same payload coordinates.

### Fleet encounters

Delivery owns the cargo, destination and deadline while locomotion, expressions, conversation and reader interaction can run alongside it. [Traffic spacing](../views/pdf-viewer/src/common/robot-traffic.ts) operates on complete carrying groups, independently of random comic encounters. Each group supplies its center, radius, ground or fixed status, priority and remaining lifetime. One shared displacement moves its bodies, photograph, refinement underlay, mast, sling and cleaner together. Rescue participants also move as one group. Ground groups yield horizontally; a ground robot being carried can follow its aircraft.

Fixed deposits and handoffs keep their anchor positions and retain ordinary weight and identifier priority. They can still yield visually when another group occupies the same space. Fixed anchors that cannot fade, including parked actors, column work and retiring fragments, take priority over movable or fadeable groups. The helper applies the caller's endpoint scale once to the returned displacement, and checks clearance using those displayed positions. Returned displacement stays within 96 CSS pixels; the 0.8-pixel-per-millisecond steering cap applies before that endpoint scale.

If bounded spacing cannot resolve an overlap, the yielding group fades out over 160 ms. It recovers over 240 ms after both its planned and displayed positions clear higher-priority obstacles by an additional 12 CSS pixels. Hidden groups remain solver inputs, preventing repeated disappearance and reappearance at the same obstruction. A payload can preserve this visibility state as it becomes fixed at deposit. Fading changes the presentation of the helpers, transported raster, refinement underlay, cleaner and attachments together; it retains the copied pixels and the opaque destination cover until the original deposit deadline. Sharper pixels can still refine a yielding payload. Recovery uses those same resources without copying or admitting another delivery. Spacing and fading preserve the payload identity, helper leases and original delivery deadline.

[The encounter controller](../views/pdf-viewer/src/common/robot-encounters.ts) can stage one brief traffic, successful-delivery or rescue incident at a time. Advancing, carrying and returning actors can participate; members of the same payload are excluded as traffic pairs. A near miss, bump or reunion changes the participants' gesture within their remaining scene lifetime. An actual or swept contact confirms a bump. Each pair must separate before it can participate again, and cooldowns bound repeated comic reactions. Successful-delivery gestures begin at an actual deposit. Carrying actors keep their handling pose while the accompanying expression or speech runs.

The shared dialogue catalogue chooses short exchanges for each encounter kind. Near misses can mention a rest or a cave detour; reunions can plan a break or a concert after delivery; successful deposits can celebrate careful handling or a musical handoff. These lines use the participating vehicles and the existing caption lifetime.

Captions group an exchange with its speaker names. They use measured, wrapped text and the shared [label-placement solver](../views/pdf-viewer/src/common/label-placement.ts) to avoid actor bodies, cargo and other labels while staying inside the visible reading area. Document speech uses fixed 12 CSS pixel text, a 16-pixel line height, 6-pixel horizontal and 3-pixel vertical padding, and weight 600. Its opaque background is neutral light grey with dark text and a blue-grey border and leaders. Grouped speech is at most 256 CSS pixels wide on desktop or 224 in compact presentation. The text size is independent of body compensation, PDF zoom and canvas backing density. Ordinary incident captions allow 1,200 ms plus 45 ms per character for reading, bounded between 1.8 and 4 seconds. A pending cue keeps its original finite expiry; its remaining reading interval starts once at its first visible placement.

Delivery name tags remain attached to the vehicle artwork. Light text, a small dark backing and a muted border keep the names readable over photographs and page backgrounds. The shared painter uses 6.5 drawing units for these compact tags; speech captions and the Lab's separate labels retain their own screen-space sizing.

At most one document work-status label is shown. Its measured bounds are cached by text, available width and font metrics. Visible grouped speech reserves its actual rectangle before a status label is placed, including when the speech remains briefly after its gesture. Blocked work-status labels and their leaders disappear immediately. Placement uses stable priority and identifier order, and only fitting labels consume an admission slot.

One caption owns its readable text and deadline independently of the actors. Ordinary hover loss, traffic fading, gesture completion, departure or promotion into cargo work removes its moving leaders and keeps the opaque bubble at its last readable page-local placement. Ordinary new cues do not replace unread text or queue behind it; an explicit greeting may replace a hover hint. The static caption uses one expiry timeout and retains no actors, cargo or animation loop. Removal of its associated visible pages, invalidated geometry or layout, hiding, reduced motion, document replacement, disabling or disposal clears the affected caption. Encounters share the normal actor budget and scene clock.

### Reader interaction and rescue

[Reader interaction](../views/pdf-viewer/src/common/robot-interaction.ts) observes passive events on the existing document container. Mouse or pen hover gives a brief carrying, preparing, returning or waiting line. A primary unmodified click on the same robot, within 8 CSS pixels of its press and within 800 ms after release, produces a greeting; touch supports a tap. The greeting gesture lasts 850 ms and its caption lasts 2.8 seconds. Hover text lasts 2.2 seconds and requests one visible paint; a parked crew then sleeps until another input or finite gesture. Static hover labels appear only when the placement solver finds room for them. Hit boxes account for native scrolling and column movement since the last paint.

The observer leaves PDF input ownership intact: it does not capture the pointer, prevent default actions, stop propagation or move focus. Links, annotations, editors, form controls, modified clicks, text selection, dragging and multiple pointers exclude or cancel a gesture. Scroll, wheel, context menus, blur and hiding cancel it as well. A carrying robot retains its cargo pose, and click speech takes caption priority.

A rare field malfunction can occur during advance or cargo work. An ordinary viable rescue has a 6% admission chance, with at least 12 seconds between attempts and the existing incident cooldown. The [rescue planner](../views/pdf-viewer/src/common/robot-rescue.ts) sums every body in the rigid casualty group and each distinct attached cargo job once. It assesses a qualified aircraft, one or two ground tow helpers, an extraordinary transport attempt, or repair in place. This uses the same structural support and outcome policy as cargo work, including a very rare small robot attempting to tow a much heavier one. A committed extraordinary rescue proceeds with its own willingness and 50% fulfillment decision. Members of the casualty group and other multi-member carrying teams are excluded from helper selection.

Rescue admission requires every participant to remain available for the full interval. An existing heroic cargo activity owns that robot through its actual deadline; the rescue checks this ownership before consuming an attempt. Each candidate supplies its current and already planned future cargo commitments. Admission prepares the complete interval assessment, and animation reads the cached phase data.

The finite rescue sequence is sputter, rendezvous, assist and rejoin. Bounded sparks and smoke identify the disabled robot; helpers lift, tow or repair the group, then return to their underlying routes. Additional carried members keep their relative offsets. A relocation records its origin, target and achieved full or partial position once at the work boundary, followed by the matching aftermath and recovery. The scene lasts 900 to 2,400 ms within the shortest participant lifetime, preserving a 40 ms ownership margin. Release and cancellation use the actual event time: elapsed work resolves first, and any remaining activity then ends. Cancellation before the work boundary records cancellation. Rescue uses the existing actors, cargo owner and delivery deadline.

### Document replacement

Each viewer engine arms replacement clearing only for its ready candidate. The controller records the document identity, generation and abort signal, then captures current visible pixels at the matching `pagesdestroy` event. Old document, preparation and preview state can be released while the retiring scene continues with bounded copied fragments and numeric viewport-relative geometry.

Desktop can capture up to three fragments per visible page and compact presentation one, within the shared actor, cargo and vehicle-backing limits. Each fragment has a 2.1-second lifetime with at most 200 ms stagger. Actors approach, pick up and carry it out. Navines can lower a bottom photograph to its carrying height and drive it out horizontally while its body stays at the page base; other ground carriers use shallow straight side exits limited to the same 0.25 slope. Cargo is released at 76% of that clock, and bodies complete their return by its end. A ground carrier returns to its lab dock only when that route is shallow enough.

Useful new deliveries can reclaim retiring fragments, the cleaner and the column-pull actor until they have capacity. Abort, supersession, trusted reader input, a new column transition, disabling, hiding and disposal cancel the corresponding retiring work. Completion removes the identity-matched abort listener. Release removes owned bitmaps, covers, masts, slings and borrowed actors; full scene cleanup also clears traffic, encounters, hit boxes, interaction state, caption expiry and scheduled frames. Parked crews and static captions keep no animation loop running.

### Motion Lab controls

A separate measurement button opens **LARICS Motion Lab**, initially closed. Its fleet dispatch area shows the crew while the document is ready. If the panel is open when a document delivery starts, actors leave from their actual positions in that area and return there afterward. Each dispatched actor is hidden in the panel until it returns. Each crew releases its reservation through the dispatch port that granted it. Closing the panel lets an active courier depart from the viewport instead.

The lab measures its actual fitted canvas, including object-fit and object-position. Body scaling is applied around each actor's center, and a borrowed actor's dispatch scale includes the fitted stage and body compensation so its visible size matches at departure and return. Actor names and notices use a separate measured label pass outside the vehicle artwork transform. The actual fitted canvas scale converts the shared 12 CSS pixel text, 16-pixel line height and 6-by-3-pixel padding into drawing units; backing density does not change their displayed size. The opaque dark-blue background, light text and muted border match the existing lab panel. The compact summary uses the same palette with normal-weight text and no border.

The [lab raster planner](../views/pdf-viewer/src/common/robot-raster-sizing.ts) derives backing density from the actual fitted CSS size and current device-pixel ratio. Density is quantized, and shrink hysteresis retains a sufficient backing through small size reductions. The main canvas, background and all cached robot bodies share a 64 MiB budget, with at most 8,192 pixels in either dimension. Replaced surfaces are zeroed before their new backing is allocated. Size and density changes request one coalesced repaint; a static lab then returns to idle. Disposal zeros every owned canvas and releases the body cache.

The lab admits at most three fitting name or notice groups. Active notices take priority over delivery and work labels, which take priority over ambient names; identifiers provide a stable order within a priority. Body obstacles, other labels and the visible stage constrain placement. Blocked or over-budget labels and their leaders are hidden immediately. A static lab makes these decisions on its one requested paint and keeps no animation loop running after finite work ends.

[The panel controls](../views/pdf-viewer/src/common/motion-lab-panel.ts) support floating, left-docked and right-docked positions. Floating and docked panels stop at their natural content height or the available viewport height, whichever is smaller. Docking keeps the displayed width. Returning to **Float** restores the remembered floating position and requested size within those bounds. The panel stays inside the visible viewport, including when the browser changes its visual viewport for zoom or an on-screen keyboard; a temporary contraction preserves the remembered floating rectangle for when space returns.

Content height is measured at the requested width from the intrinsic flow, independently of the fixed panel and scrolling area. Width changes, wrapped text, disclosure changes and responsive layout can update the ceiling. Passive updates preserve the requested height. Opening **Motion and buffer measurements** fits the expanded content while retaining width; closing applies the lower content ceiling and preserves a manually shorter height. The ceiling also limits manual vertical growth and the minimum height, so a short panel has no empty lower tail. Content changes keep the chosen dock and notify the same document-column owner as other geometry changes.

### Document position beside the Lab

The panel reports changes through `onPanelLayout`, including visibility, dock side, rectangle and the reason for the change. Rectangles use CSS pixels in the same coordinate system as `getBoundingClientRect()`. The callback receives its own rectangle copy, and closing or disposing the panel reports `visible: false`. A docking scene publishes its destination once, so the column plans against a stable target. While column work is pending, the callback returns its current `readyAt` estimate and an `isReady()` check. The panel retains that preparation through any continuation and starts its glide only when clearance is actually ready. Changes to the panel's painted rectangle separately invalidate fitted lab geometry and courier destinations; intermediate animation frames do not publish new column targets.

[The document-column helper](../views/pdf-viewer/src/common/pdf-document-column.ts) measures visible page containers, including both pages of a spread. A right dock moves the document left to avoid the panel with a 16-pixel gap, limited by the blank margin on the left. A left dock uses the corresponding blank margin on the right. If the pages fill the reading width, they stay in place.

A floating Lab can also move the column aside, but only when the complete visible page or spread fits on one side within the reading viewport with the same 16-pixel gap. If neither side fits, the column returns to its original position instead of pushing pages into clipping. If the original column already clears the panel, it recenters. Otherwise each feasible side supplies its smallest necessary displacement from the original column. The helper chooses between those targets by distance from the current offset and preserves the selected side on ties, including during the stationary approach before its first frame. Shrinking the Lab therefore brings the column back on its existing feasible side instead of leaving an unnecessary offset. Closing the Lab or moving it outside the visible pages' vertical span also restores the original horizontal position.

Pages and registered robot layers receive the same horizontal CSS translation. Page width, zoom and scroll offsets stay unchanged. The helper subtracts its current offset from measured page bounds before calculating the available margin, so repeated measurements cannot accumulate an offset. Robot layers must be disjoint roots, such as the transit container; the renderer accounts for the offset once in its screen coordinates.

[The shared choreography](../views/pdf-viewer/src/common/motion-lab-choreography.ts) lets drag, resize and viewport changes settle for 300 ms before starting column work. During that interval, the latest requested placement replaces the pending target. An already committed leg finishes on its original deadline; subsequent input cannot repeatedly restart it. Open, dock and close actions can start a leg immediately when none is active.

Each column leg lasts 2,500 ms: 500 ms for the actor to approach its stationary edge, 1,800 ms for the haul, and 200 ms to settle. The haul eases smoothly into and out of motion. If another target is still settling at the end, the column and its forklift park at the completed edge. Once settled, the latest target receives another finite leg. A docking or Float action waits through this work before gliding the Lab to its destination over 1,200 ms. That glide has its own fixed deadline once started. If the column is already positioned, it can start immediately. Taking direct control cancels the panel animation at its displayed position. Reduced motion and document hiding settle pending geometry immediately. Disposal restores the previous column styles and removes observers, listeners, pending timers and frames.

An actual finite shift can summon one available Navines to the relevant document edge. It approaches during the initial 500 ms and keeps its pull attachment on the edge through the haul and settle phases. The same actor, sprite and Lab reservation remain available while parked and through a continuation, whose approach begins at the displayed position. Parking uses no animation frames merely to hold the pose. After the final requested position is reached, Navines returns for at most 650 ms. A reachable lab dock is used when the ground route is shallow enough; otherwise it leaves horizontally. The scene shares the actor budget and skips admission when a forklift is already busy. The column can still move when a forklift is unavailable. Early cancellation, new delivery work, trusted reader input, hidden or empty pages and teardown release the actor.

The reader's `data-pdf-column-moving` attribute covers pending input settlement, column legs and continuations. The panel's `data-panel-moving` attribute covers its readiness wait and glide. Completion or cancellation removes each marker, restoring a prior column marker value if necessary. Input settlement uses one owned timeout, and each owner stops requesting animation frames when its work ends. Settled controls and column geometry keep no idle animation loop running.

### Measurements

[The diagnostics module](../views/pdf-viewer/src/common/prefetch-performance.ts) samples every 250 ms while open. Its charts cover ten seconds; event storage holds the newest 512 events and transfer storage the newest 2,048 samples. Closing the panel or hiding the document stops chart sampling and lab animation. The document effect has its own finite scheduling and works with the lab closed. `installPdfPrefetch` accepts `diagnosticsToolbar`, an optional `robotsEnabled` preference, and an independent `diagnosticsEnabled` initial preference. The controller snapshot includes bounded document-robot counters and the optional lab state for performance inspection.
