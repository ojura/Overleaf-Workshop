# Slipstream: predictive PDF loading

Slipstream is the shared viewer, predictive loading, and cache layer behind both extension engines and the standalone [Spomenar site](spomenar.md). They use the same controller, [pdf-prefetch.ts](../views/pdf-viewer/src/common/pdf-prefetch.ts), with PDF.js 5.1.91. Each passes its `PDFViewer` to `installPdfPrefetch` once during startup. Document replacement resets the controller through the page lifecycle events. [scroll-prefetch.ts](../views/pdf-viewer/src/common/scroll-prefetch.ts) owns the motion estimator and device cache policies.

## Reading position and page lifetime

Both extension engines use [reading-state.ts](../views/pdf-viewer/src/common/reading-state.ts) to capture the actual visible page, its PDF coordinates and zoom on the existing scroll and view-update events. A raw scroll can arrive before PDF.js updates its current page number, so capture uses the first visible page's geometry. Restoration uses the same PDF coordinates, including signed offsets within page margins, suppresses intermediate captures and publishes the completed view. The page updates its VS Code state and sends the same snapshot immediately.

[PdfViewState](../src/core/pdfViewState.ts) coalesces durable storage in the extension host. Received state remains available to a replacement page while an earlier storage write is pending. Writes execute in order against the current saved-state map, and hiding, switching or closing the viewer flushes the state the host already received. Ready and state messages name the current page; a replaced page cannot overwrite the new view. Delayed HTML generation also checks that its page still owns the panel before assigning the result.

The full PDF.js adapter observes its startup event and initialized promise. Closing the page removes those listeners and cancels pending loads, including a validated candidate waiting for the old document to close. Both extension adapters consume the shared [viewer policy](../src/core/pdfViewerPolicy.ts) for button and keyboard zoom and the worker-destruction allowance. The standalone lifecycle uses that same allowance. Completed or rejected destruction clears its fallback timer; a worker that never answers still has a finite release path.

## Scheduling and cache layers

The estimator follows CoS's `TimelineScrollDynamics`: react immediately to faster motion or a slower page, then decay the estimates gradually. Wheel events predict motion before the next scroll frame; the controller avoids counting that movement twice. Scroll events cover keyboard navigation and scrollbar movement. The selected policy's gesture gap clears velocity and acceleration, while the document's loading-time estimate remains available. The default is 250 ms; the estimator and controller settlement timer receive the same value. Acceleration is diagnostic; velocity, the latest displacement, and measured page latency determine the preload distance.

[Render timing](../views/pdf-viewer/src/common/pdf-render-timing.ts) excludes measurements made while the browser withholds rendering frames. While measurements are active, one probe requests a frame and starts a one-second timer. If the timer arrives within 100 ms of its deadline but the frame has not arrived, the active measurements are discarded. A late timer can reflect substantial foreground work, so that delay remains part of a valid render measurement. Cancellation, invalidation and disposal release the probe; it stops when the last measurement finishes.

The desired distance starts at two viewports, with a 480 px minimum. It grows with speed and page latency, up to twelve viewports or 12,000 px, whichever is smaller, while preserving the base distance for large viewports. Direction changes immediately on reversal.

The controller uses five cache layers:

1. The extension keeps verified content-addressed pieces and incremental range blobs on disk, under one budget across all builds.
2. PDF.js stores received bytes as sparse chunks within its active document.
3. Prepared PDF pages retain PDF.js display operators and decoded resources.
4. Small raster previews cover pages while full-resolution rendering catches up. Mobile retains nearby previews at up to 512 px and reduces older detached previews to 192 px before eviction.
5. PDF.js owns the full-resolution page canvases and their rendering queue.

The persistent [disk cache](../src/core/pdfDiskCache.ts) accepts complete GET requests to `/content/<contentId>/<SHA-256>` when the response bytes match the hash, and verified `output.pdf` ranges with stable validators. A build is represented by byte-interval metadata and received blobs. The host fills missing intervals gradually while every visible reader is idle. The configured `pieceCacheSizeMB` budget, 4096 MiB by default, includes old and new builds, reusable content pieces, range blobs, metadata, and bytes reserved for current writes. A new build does not create a full-size file. `0` disables disk caching and background fill.

The cache owns its operation queue and short writer leases. Network transfers run outside the writer lease and foreground read queue. Exact-build exports use the same cache admission and cancellation machinery.

Each cached single or multipart response captures one manifest, validator, segment list and complete set of ordered read plans before reading bytes. A concurrent host can publish a new representation without mixing it into that response. If any captured immutable blob disappears, the entire cache hit is rejected. `If-Range` requests use the origin path so its [HTTP conditional-range rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.5) decide whether the range applies; a whole-document `200` is canceled before its body is read.

The [pinned PDF.js patch](../views/pdf-viewer/vendor/pdfjs-5.1.91-dist.patch) adds `rangeCacheBytes`, `getRangeCacheStats()` and `trimRangeCache()` to the same runtime used by both engines and the website. Reading a range checks that each chunk is resident, including the initial progressive prefix. Old chunks can be fetched again after eviction. Active parsing, asynchronous page work, rendering tasks and detached image decodes hold the bytes they may still need. Once those operations finish, the worker trims its LRU to the selected budget.

The worker budget is its idle residency target. One active PDF stream can exceed it temporarily, so the shared controller also stops new cold-page work while the byte cache is over budget. A completed preparation keeps its admission slot until the worker has answered a trim request. Running and fully prepared native pages can continue. A 250 ms memory check runs only while work or memory pressure remains; it operates even with Motion Lab closed, and stops when the document is hidden or disposed. This lets ongoing work finish and gives the worker a chance to release bytes during continuous scrolling.

An image acquires its range hold only after the decode queue admits it. The hold covers image construction, asynchronous decoding and missing-range retries, then releases before the worker trims between queue slots. Queued images can refetch evicted source bytes when admitted. This prevents a long image queue from holding the complete range cache above its idle target.

Preparation uses small `pdfPage.render()` calls with the display intent shared by native rendering. At most three cold pages on desktop, or two on mobile, are admitted across speculative previews and the auxiliary renders that track native resource preparation. A new cold native render starts only after its small auxiliary render is running. That auxiliary render holds its slot until preparation actually completes. Completed native renders and previews mark resources warm; PDF.js clearing the same page proxy's rendering-intent map revokes that status.

Native visible pages and holes in spread layouts retain their rendering priority. An uncovered visible page blocks further offscreen admission. When scrolling makes an already-started preview obsolete, it becomes `retiring` and finishes while holding its slot. This prevents repeated canvas cancellation from launching unbounded worker decoding. Obsolete `getPage` requests whose render has not started are discarded. Document replacement, layout changes, hidden documents, and disposal still cancel work; completion checks reject stale results.

When a native page pass is cancelled, its owning page view returns to `INITIAL` and clears the paused continuation before releasing that task. The existing rendering queue can then retry the page when it becomes eligible again. For external-image redraws with a preceding accepted canvas, the cancellation callback restores that canvas. The cancellation callback and final cleanup check the same task identity, preserving any newer task, continuation, rendering state and canvas. The shared build transform applies this rule to both viewer variants, including an already transformed full viewer.

During mobile motion, a visible page whose compatible nonempty preview is attached to the current page waits for the existing gesture-settle event before starting cold native preparation. Warm and already-running work continues. Missing, detached or invalid previews retain immediate native fallback. This keeps fast traversal from decoding each passing page after the preview already supplies its displayed pixels.

Full-resolution lookahead stays within two viewports. Counting visible pages and spread holes in that window avoids repeatedly evicting and redrawing pages through PDF.js's default ten-view buffer. Rotation, theme, and optional-content changes invalidate saved previews; zoom can reuse and resize them. Disposing the controller removes listeners and restores the queue methods.

On both device policies, a retained distant preview is sufficient coverage without keeping decoded photo resources. Finished native canvases release their operator lists and every decoded resolution tier, including when the canvas is still visible. External-image pages retain resources until their pending refinements reach final painted quality. The explicit `releaseRenderedResources` policy is separate from mobile's `pruneOffscreen` canvas policy: desktop retains its larger native-canvas window. PDF.js defers resource cleanup until every active render and its operator list have finished. The native canvas and retained preview remain ready, and neither starts another decode merely to warm resources again. A later zoom requests fresh rendering at the new scale.

The [graduated preview cache](../views/pdf-viewer/src/common/pdf-preview-cache.ts) protects visible, attached, and prepared rasters, reduces the oldest unprotected entries first, then evicts only if needed. A returning finished native canvas upgrades its smaller trail preview with `drawImage`, without decoding the PDF again. Replacing an attached raster publishes its new node before releasing the previous bitmap. Failed admissions and canvas-allocation failures wait for the visible-page plan to change instead of retrying on every refresh.

### Raster and page coordinates

The shared [raster projection module](../views/pdf-viewer/src/common/pdf-raster-projection.ts) maps normalized logical page coordinates to backing pixels and to displayed CSS pixels. It keeps the full logical content rectangle separate from the visible page clip. PDF.js rounds its canvas backing and CSS dimensions while retaining the unrounded render viewport; using the rounded page box as the full logical page would shift and scale previews and photograph masks. The observed 50% Antigravity view, for example, has a 332.599 × 472.441 CSS-pixel logical page inside a 330 × 470 clip, with a 396 × 564 native backing.

Each preview retains its projection with its canvas. Atlas images cover the complete normalized page. Independently rendered previews retain their unrounded viewport within the ceil-sized backing. Native copies retain the original viewport and actual output scale captured at the main `pagerender` event, including any clipped edge. Cache resizing scales that mapping independently on both axes. CSS-only rotation changes the logical basis of the retained pixels, so a clipped edge moves to the correct side without another full-page bitmap. CSS-only zoom derives displayed content from that saved mapping and the current native canvas box.

A main draw can allocate its native canvas before attaching it. Until that canvas has a display box, the ready preview uses the current logical viewport and page clip. The provisional geometry remains uncached so the next update can measure the attached canvas, even when the viewport has not changed.

Photo crops read outward from the floor of each source start to the ceiling of each source end. The bounded cargo canvas applies the exact logical transform, so the extra sampled edge pixels do not stretch the photograph or change its landing target during refinement. The source cover rounds outward on the displayed raster's pixel grid, adds one physical display pixel to cover fractional compositor edges, and clips to the visible page. That margin is `1 / (devicePixelRatio * visualViewport.scale)` CSS pixels, with a scale of one when the visual viewport is unavailable. Preview clipping, source sampling and cover placement use the same projection helpers in both extension engines and Spomenar.

### Display-sized image decoding

`pdfDocumentCacheOptions()` supplies the same document options to the extension's two engines and Spomenar. Both device policies enable adaptive display-image decoding. Mobile admits one image job per document; desktop admits two while retaining its three cold-page preparation slots and larger raster budgets. These limits cover image construction as well as decoding: one admitted collage page can contain many large photographs. Printing requests original detail.

The display proxy derives image density from the page viewport and actual output transform. Auxiliary previews request the native canvas's density so they can prepare the same decoded resources. Resolution is part of the display-intent identity; a prepared higher-resolution intent can satisfy a smaller render, while a larger zoom requests new detail. Warm-resource records carry the same density and are rejected if the new zoom needs more pixels.

The worker composes each image's placement matrix, including nested Form matrices, and rounds the requested dimensions upward. Repeated image XObjects at different sizes have separate cache entries. Tiling patterns use a conservative page-sized bound when the placement cannot be determined. Adaptive intents avoid the original reference-only global image cache, which could otherwise reuse a smaller image at a larger zoom.

Plain, unmasked DeviceRGB JPEGs decode directly to their required bitmap dimensions through the browser's native decoder. Orientation, color conversion and alpha premultiplication options are explicit, and the existing PDF.js JPEG compatibility checks and EXIF removal remain in use. A decoder that returns the wrong dimensions has its bitmap closed. If the native path is unavailable, a fresh JPEG decoder produces scaled pixels; reusing the same compressed stream at a later zoom therefore cannot reuse an earlier small output buffer. Other image semantics keep the existing PDF.js decoding path.

Active image jobs validate their encoded source and mask ranges before construction, then retain those ranges until decoding completes. Incremental decoders therefore start with resident bytes even after their queued sources were evicted. Document termination rejects waiting jobs and closes late native bitmaps. Image statistics travel with the existing range-cache statistics request, so the feature adds no separate polling loop.

### Transfer admission

PDF.js can continue worker image and range requests after a render task is cancelled. Before admitting a page whose resources are cold, the controller also checks unfinished viewer fetches. On desktop it pauses new cold native renders and cold preview preparations when at least twelve fetches are pending, or when at least six are pending and the oldest has reached 1,500 ms. Mobile uses thresholds of six and three respectively. Existing running or paused native renders can continue or resume, and pages with fully warmed resources can render from those resources.

These are admission thresholds: one admitted page can request several images, so the number of pending fetches can exceed its threshold. `onFetchChange` schedules a coalesced refresh as requests finish, allowing waiting work to resume from observed completions. The cold-page limit also includes work still decoding after its transfers finish.

### Host response ownership

The shared [bridge response helper](../views/pdf-viewer/src/common/bridge-response.ts) consumes bytes that have already arrived in a private host message. It transfers the owned buffer into a native byte stream instead of copying it into `Response`, then reads that one complete chunk directly. Full-span chunks reuse their transferred backing buffer; sliced views get one exact-range copy so neighbouring bytes cannot escape. Transfer accounting runs before enqueue detaches the original buffer.

The build adapts exactly two response-consumption sites in the pinned Overleaf loader, and stops if their source no longer matches. Both extension engines use this path. The original HTTP responses used by Spomenar follow native `arrayBuffer()` consumption. Cloned, locked and consumed responses also keep native handling; [Fetch's body-clone operation](https://fetch.spec.whatwg.org/#concept-body-clone) replaces the original stream with a tee branch, so neither clone branch is marked for direct consumption. Final PDF range reassembly still owns a separate buffer for transfer to the worker, preserving chunks retained by the incremental loader.

### Budgets and thresholds

The authoritative values are selected by `pdfCachePolicy()` in [scroll-prefetch.ts](../views/pdf-viewer/src/common/scroll-prefetch.ts). Phones and tablets use the mobile policy, including iPads with desktop-mode user agents. A touchscreen desktop keeps the desktop policy. Callers can provide an explicit `cachePolicy` to the shared controller.

The policy separately owns sidecar browser decoding through `sidecarDecode.concurrency` and `sidecarDecode.maxInputEdgeScale`, a multiplier of the retained preview edge. `pdfSidecarDecodeOptions()` derives those consumer limits in the same module. Legacy custom policies without the optional setting retain the previous named-profile fallback. Sidecar decoding and PDF worker image jobs remain independent consumers with explicit budgets.

| Resource | Desktop | Mobile |
|---|---:|---:|
| Planned preparation window | 16 pages | 6 pages |
| Cold page preparations, including pending `getPage` and retiring jobs | 3 | 2 |
| Pending-fetch threshold for pausing cold work at any age | 12 | 6 |
| Pending-fetch threshold when the oldest reaches the age limit | 6 | 3 |
| Oldest-fetch age limit | 1,500 ms | 1,500 ms |
| Full-resolution targets, including visible pages and spread holes | 8 | 3 |
| Full-resolution canvas admission and cleanup target | 192 MiB | 48 MiB |
| Preview maximum dimension | 768 px | 512 px |
| Distant trail preview maximum dimension | No downsampling | 192 px |
| Retained preview raster storage | 64 MiB | 8 MiB |
| Retained preview count | 128 | 128 |
| Sparse worker byte-cache target | 128 MiB | 32 MiB |
| Concurrent adaptive image jobs | 2 | 1 |
| Active progressive input, coefficients and partial rasters | 192 MiB | 64 MiB |
| Encoded input bound per external image | 32 MiB | 32 MiB |
| Retained coefficient bound per external image | 64 MiB | 64 MiB |

Visible pages remain protected. Mobile destroys native canvases outside its current visible/render-ahead plan when their active preparation has finished, even when their total is below 48 MiB. It retains the graduated preview LRU for revisits and releases unneeded display resources. PDF.js also maintains decoded resources outside the raster byte counters.

## Structural reading documents and progressive images

The optional [reading representation](motionlab-reading.md) keeps the original PDF as the source and download identity. Its small structural PDF retains native page operators, fonts, image dictionaries, masks, filters and geometry; verified external assets supply the image bodies. Both extension engines and Spomenar pass the validated source to the same patched PDF.js runtime. The [reading loader](../views/pdf-viewer/src/common/pdf-reading-source.ts) validates the original digest, size, page count, derived PDF digest and every image chunk before handing bytes to the worker. Producer, loader and worker consume the same [format definition](../src/core/pdfReadingFormat.json); device admission limits remain in `pdfDocumentCacheOptions()`.

Native text extraction and the first page pass can finish before the photographs. Image placeholders occupy their original positions in the operator list. Each installed image revision schedules one coalesced native replay through the existing rendering queue, preserving the PDF's actual clipping, transforms, masks and paint order. `imagePassRevision` and `imagePassStatus` describe the attempted pass; `paintedImageRevision` and `paintedImageStatus` describe the successfully published pixels. Available image resources, a completed render, useful displayed coverage and final native quality are separate facts. A replacement may publish only after its native task succeeds and its coverage satisfies the display rules below. A failed or cancelled task retains the preceding displayed canvas and its evidence, including when all image resources had already finished decoding.

The worker retains progressive coefficients between scans and can compact a first-DC result while another image receives initial coverage. The active-state cap includes retained encoded bytes, coefficients and partial rasters. Final decoding uses the normal native/filter path with the already verified bytes and the existing page-object lifetime; its raster bytes are measured separately. Offscreen pages, hidden documents and disposal cancel unfinished page epochs. A changed render scale can replace a decoding epoch while preserving the same source page's displayed pixels and logical delivery work. The cancellation promise resolves after owned worker state is released. Final painted pages are kept ready without restarting their image jobs.

The extension discovers `reading.json` beside an exact-build preview registration. Its image bridge accepts only the registered manifest revision, image ID, starting chunk index and optional chunk count, which defaults to one. The count selects a contiguous part of the validated scan partition; original encodings remain one whole asset. The loader and host use the same selection helper, and both verify every selected chunk before returning a combined response. The host reads that authorized range from a regular local file and returns exact range metadata. This avoids depending on an IDE resource service's Range support. The website uses strict HTTP `206` and `Content-Range` checks for partial ranges; an ignored Range response is cancelled before its full body is read. Mutable manifest URLs revalidate, while immutable digest-bound image and structural PDF assets retain ordinary caching. Cancelled reads keep their admission slots until they settle. A batch is one transfer in the existing bandwidth and latency measurements; its event retains the first chunk, count and first/last scan numbers.

A new reading-manifest revision for the same original edition prepares before replacing the displayed document. The old controller suspends new speculative work and awaits its image cancellation barrier while preserving displayed canvases. Candidate visible pages prepare the adopting viewport, output density and annotation intent on a clipped 2×2 destination, then await usable image coverage. A changed intent is released and prepared again before adoption; cancellation resumes the original owner. The final reading position is captured at adoption, and the change does not announce a new edition or replay edition teardown. Download commands continue to use the original PDF.

Fresh structural loads use the native text/image path and read atlas metadata for semantic image regions without fetching the full-page raster tiers. Their acceptance measurement records first visible photo pixels, complete painted coverage of both visible pages, sharp/selectable text and final quality separately. The normal raster path below remains available when no verified reading representation exists.

All reading transfers feed the existing fetch throughput, duration and active-request measurements exactly once, including host-delivered chunks. The page-ready estimate spans the first native pass through first complete painted image coverage; short later replays do not replace that delivery cost. `pdfPrefetch.snapshot().performance.reading` retains cumulative manifest/PDF/image bytes and native pass costs beyond the event ring. The existing `rangeCache` report carries active, queued and paused image work, encoded/coefficient storage, partial raster reservations and final native raster storage. `imagePages` exposes installed, attempted and painted revisions plus first coverage/final times. These reports use the existing bounded collector and unsettled-work sampling, with no separate idle poll.

### Display ownership and successful candidates

The following ownership rules apply across native rendering, previews and document deliveries. They keep automatic refinement separate from a new loading episode.

| State | Authoritative owner | Publication rule |
|---|---|---|
| Decoded image objects, pending work and failures | PDF.js `PageImageRevisions` and the external-image worker | Report the registered object and source image identities for the current image intent; one failed image does not finish other pending images. |
| A native page candidate | The actual PDF.js render task and page view | Capture its resource membership, image-operation evidence, logical appearance and raster geometry, then accept it only after the complete task succeeds. Resource availability alone cannot publish a canvas. |
| The displayed page raster | One shared page presentation decision used by native and preview publication | Commit the canvas, projection, appearance identity and successful coverage together. Require its backing to remain connected inside the current page element. |
| Prepared page pixels | The retained preview cache and validated native presentation | Count usable cached pixels for the buffered reading distance; require an accepted connected raster for visible coverage. |
| A visible page's logical work | `pdf-prefetch.ts` | Distinguish queued work, active preparation, useful coverage, refinement and terminal completion or failure independently of `INITIAL`, `RUNNING`, `PAUSED` and `FINISHED`. |
| Selected delivery regions and their covers, cargo and actors | `PdfDeliveryPlans` in `pdf-delivery-plan.ts`, with the renderer adapter in `pdf-document-robots.ts` | Commit a bounded plan once, preserve its identities through refinement, and resolve each selected region exactly once. |

A candidate belongs to one document generation, source page and logical appearance. The controller gives each page number one source-page identity within the document. Native publication, early previews, image-source updates and delivery cleanup use that identity even before the native `PDFPageProxy` has been installed. The actual proxy binds separately when available; a conflicting proxy is rejected. Installing the proxy, replacing a page DOM node, evicting pixels or changing scale preserves the source-page identity and its delivery history. Document replacement clears it.

The controller supplies one `imageAppearance` identity for native and verified atlas candidates; the native pass captures it when rendering starts. Source-page identity fixes the PDF page geometry. Rotation, optional-content configuration and colour treatment change logical appearance; first proxy installation, scale, output density, scrolling and spread arrangement preserve it. `rasterGeometry` separately records the actual native viewport and output transform used for pixel comparison. A render attempt has its own identity within that lifetime. Before committing a candidate, reject stale document/page owners and incomplete or failed attempts.

For partial replay within one intent, appearance and raster geometry, compare the covered native object identities rather than counts alone. A replacement intent or incompatible raster geometry retains the preceding raster until complete successful coverage is available, unless an explicit occurrence mapping establishes an equivalent coverage comparison. For a successful native predecessor, a known empty covered set after complete registered-resource discovery permits the empty-set comparison for a compatible successful partial candidate. Successful-task, source and appearance checks still apply. This evidence concerns registered external-image objects; ordinary inline, mask and other native image operations can already have painted pixels. The exception does not apply to complete atlas previews or unknown legacy coverage. Missing resource metadata must never become an empty set by default. A deliberate appearance change establishes a new appearance identity; old previews cannot restore the preceding layer or colour choices.

A displayed candidate must belong to the current document and source page, retain a positive canvas backing, and be connected inside the current page element. A canvas can retain its `parentNode` inside a detached wrapper, so parent presence alone does not establish display. Visible coverage, pixel borrowing and delivery reconciliation read this validated candidate and its successful coverage. Pixel borrowing derives the current display projection from the recorded raster geometry, including any CSS rotation. Historical `paintedImageStatus` remains a report of an earlier native publication; it cannot establish that its pixels are still displayed.

The preview cache carries successful coverage with its projection and raster. A copy of a native canvas inherits that canvas's evidence; resizing changes its projection without inventing a newer content revision. A verified atlas raster represents the complete page for its bound source and appearance. Prepared cache availability and visible coverage are separate checks: a retained detached preview can contribute to the buffered reading distance, while a visible page needs an accepted connected raster. The cache must still contain usable pixels; a final status without a retained canvas does not count as prepared.

Atlas raster requests are suppressed when an accepted connected native candidate already provides complete coverage. A failed `FINISHED` native pass without an accepted raster leaves verified atlas fallback available. Structural reading documents retain their metadata-only atlas policy.

Selecting a preview or native candidate must preserve the already displayed photographs. Starting or finishing a native pass is not itself a reason to switch the displayed source. An accepted native publication commits its canvas before removing the accepted preview in the same synchronous transaction. A rejected partial pass keeps that preview attached, including after native eviction and return. The `.pdfPrefetchPreview` visibility rule implements the selected presentation; a cache entry or transient rendering state must not independently choose it. Rejected or throwing attached-preview publication releases the incoming bitmap and retains the preceding cache entry.

Actual canvas removal or eviction retires the missing presentation authority and releases its page protection. A useful partial return can then publish if another displayed predecessor is not retained. This raster lifetime is separate from the delivery ledger: removing pixels preserves every committed selection and its exposure history.

The controller owns a page's pending-work state through `getPageLoadingState(pageNumber)` and announces changes with `pageloadingstatechanged`. Pending work includes initial, running or paused native rendering, preparation and preview requests, unresolved image discovery or resources, required native replays, restart obligations and unfinished cancellation. Completing one native pass does not settle those other owners. The full viewer queries this state in its render and page-change handlers and on the semantic event; an unmanaged viewer retains PDF.js's native behavior. Disposal restores the prior hook.

The current-page toolbar indicator follows that pending-work state continuously, including refinements after useful pixels exist. The page's `loadingIcon` and `loading` classes instead describe an initial page without useful displayed pixels. A retained accepted preview or native canvas keeps that page icon absent during replay; genuine removal without a replacement restores the initial-loading behavior. Loading labels and advance crews follow their logical work and retain their existing parked state across ordinary replay changes.

Pending and failed counts remain independent: a failed first scan can coexist with other active images, and cleanup retains the resources those pending images still need. The native revision event settles the page explicitly when discovery is complete and its jobs have finished. A terminal partial failure preserves useful pixels, releases waiting delivery reservations that can no longer succeed and reports the failed page without continuing to report it as missing or starved. Once its final required native attempt and other owned work finish, the controller can become idle. Parked crews retire when their producer finishes or fails. An explicit retry starts a new work attempt; ordinary telemetry refreshes do not.

## Early page previews

Both extension engines and Spomenar use the same [preview-source consumer](../views/pdf-viewer/src/common/pdf-preview-source.ts). The [Motion Lab postprocessor](motionlab-previews.md) prepares 192, 512, 768 and 1536-pixel page images with their intrinsic CropBox orientation and optional photograph placements. These small assets can cover a page while PDF.js prepares its original resources. The shared preview cache owns admitted canvases, so sidecars use the same retention and eviction budgets as previews rendered by PDF.js.

Every source is bound to the exact installed `PDFDocumentProxy`, document identity, byte length and page count. The extension uses its canonical cached-build key and an export receipt; Spomenar additionally matches the published digest against the PDF transport's observed size and HTTP validator. The host watches atomic manifest publication and announces changes to the correct webview generation. An absent or rejected sidecar leaves native rendering available. Idle viewers do not poll for another manifest.

The native Overleaf viewer can defer document installation through `startViewTransition`. Its [preview binding](../views/pdf-viewer/src/common/pdf-preview-binding.ts) waits for the actual installed proxy before attaching a preview source. Antigravity stores the host preview root as a `vscode-userdata` URI while local preview descriptors use `file:`. The webview resource permission converts that exact root to a file URI at the resource boundary.

The native [document manager](../views/pdf-viewer/src/overleaf/documents.ts) keeps the displayed document and its loading task alive while a candidate is validated. It waits for the real viewer setter and the wrapper's completion before announcing the new build, retiring the previous task and attaching the candidate's preview metadata. A cancelled delayed callback is rejected before it can assign either the viewer or the link service. The build's checked adaptation handles the transition's `updateCallbackDone` rejection, while the manager retains the candidate's success or failure outcome.

Range and inline replacements share one [temporary height owner](../views/pdf-viewer/src/common/document-height.ts) per viewer element. The hold starts at actual assignment and preserves the preceding page height until `pagesinit`. Abort or setter failure releases its listener and restores the previous style; a superseding hold releases the older owner first. The full PDF.js entry point announces the new build after `load` succeeds and closes a partially installed candidate if its viewer setter fails. Optional scene preparation can fail without preventing a ready document from opening.

The loader gives every uncovered visible page its smallest usable image before refining either half of a spread. At most two requests occupy the pipeline; cancelled requests retain their slots until cleanup finishes. Phone image decoding is serialized and capped at a 512-pixel longest edge. Desktop permits two decodes with an input edge of at most 1536 pixels, retaining its normal 768-pixel preview size. Encoded dimensions, declared byte counts and SHA-256 are checked before browser decoding; the decoded dimensions are checked again before publication. Hidden documents, replacements, incompatible themes or optional-content changes cancel the binding, and late bitmaps are closed.

## Document deliveries and diagnostics

The SVG robot button in every viewer header enables the document effect. It starts on when no visibility preference has been saved and remembers both OFF and ON across reopening. The standalone website uses its own guarded site-wide browser storage. Both extension engines share the application-wide `overleaf-workshop.pdfViewer.robotsEnabled` setting across all documents, and open viewers follow changes without reloading or replacing reader position, theme or layout. Old per-document visibility fields are ignored. Host initialization resolves before any default robot allocation, so saved OFF cannot flash an initial crew. A newer explicit toggle wins over pending restoration, and disposed controllers cannot apply or write a late preference. Storage failure leaves the current toggle usable. Visibility remains independent of the Motion Lab and its measurements disclosure.

Eligible selected regions start transport at their first substantial visible encounter when their source pixels and physical capacity are available. Prefetched pages retain this effect by preparing a bounded delivery plan and lightweight covers before their photo-bearing canvas becomes available for reader exposure. Offscreen preparation starts no actors or cargo. The controller uses an existing successful native canvas or preview without starting another render for the effect. A preview and its native replacement share the same plan for their source page; revisiting, zooming or toggling terminal work does not repeat it. Text selection and document controls remain available, and lack of animation capacity reveals readable pixels immediately. Ready work uses available capacity during speech. A crop waits only when the next admission needs resources still owned by an admitted speaking cast. Its existing plan and cover stay queued until that finite work releases enough capacity, and the normal capacity notification retries admission without consuming the crop as a skipped delivery. Released removal pixels do not count as retained capacity.

During active scrolling, transport starts when the page's visible inner clip reaches the reading viewport's midpoint along the scroll axis, or when the page fits fully inside that axis, and the selected region meets its visible-area requirement. The same rule applies in both scroll directions and horizontal layouts. The controller also recognizes a changed scroll position before the scroll listener runs. Once the existing scroll-settle event fires, a usable partial view can start immediately. These conditions govern actor/cargo admission, not late cover creation. Selection and protection can precede the encounter. A visible region that still cannot meet admission geometry when scrolling settles is skipped and revealed; it does not remain hidden waiting for more reader motion.

Before pixels arrive, a visible duplex can receive one advance crew for its actual `.spread` membership. The crew enters and coordinates for a finite interval, then parks without scheduling animation frames while its logical work remains pending. Only an actual admission or handoff changes that choreography; native replay states, changing message text and progress counters do not restart its gesture. Staging reserves no cargo and does not mark a page as delivered. A continuing physical spread retains its group, label and actors when visibility moves between its halves. Reconcile the new members before removing obsolete visibility. A staged crew whose original staging page leaves the useful view must be handed over or retired explicitly; an admitted payload keeps its own page target. Hidden, removed, terminally failed or replaced work releases waiting reservations; reduced-motion mode shows static status.

### Photo arrivals and refinement

The finite representative-photo selection remains bounded by the existing region, actor and byte limits. Commit that selection before the chosen pixels can first become exposed. Each selected crop has an explicit queued, active, delivered, skipped or cancelled state, plus protected or exposed presentation state. The plan owns its lightweight cover from initial protection through final release. A queued entry retains normalized geometry, occurrence/resource requirements, policy decisions and its cover, without retaining a source canvas, allocating cargo or reserving actors. A payload adopts that same cover when transport starts; it does not remove and recreate it.

DOM publication and reader exposure are different events. A canvas can be connected outside the reading clip long before the reader reaches it. Once connected without protection, however, browser scrolling can expose it before another JavaScript callback. Therefore publication of a photo-bearing connected candidate without an existing cover irreversibly marks the affected region as potentially exposed. Later visibility observations cannot prove that it was never seen. The renderer must not add a cover to such a region, even if its latest sampled position is offscreen. A cached bitmap that has never been attached can still receive a plan and covers before attachment.

A successful native pass can publish useful text without creating or exposing a delivery plan when discovery is complete, `untrackedImageOperations` is explicitly `false`, and every registered resource is uncovered. PDF.js derives that flag from the completed operator inventory: recognized image paints must reference records belonging to the pass, and indirect image paths such as patterns, masks, inline images and Type3 glyphs remain conservative. Both direct font selection and ExtGState font installation participate in that proof. A missing flag remains unknown. This rule works before the preview source is even bound. If trustworthy placement metadata arrives after text but before the first photo candidate, that candidate can establish its finite plan and covers before publication. If photo-bearing or unknown pixels arrive first, their committed exposure history prevents later metadata from adding covers. With no metadata, useful text still publishes immediately; the ordinary completed-raster fallback is available only at its first still-unexposed publication. A complete empty occurrence inventory, paired with a discovered native resource list that is also empty, is another no-photo case. An empty registered-resource array alone establishes neither absence of native images nor permission to reopen an exposed plan.

Before publishing an offscreen candidate, select the bounded representative regions from its known page geometry and the full normalized page as the planning clip. For a page already intersecting the reader, use the current normalized clip, subject to its exposure history. Keep the existing crop, collage, fixed-grid portion and fragment-count limits. This earlier planning can select a different representative portion from one chosen after scrolling; it cannot grow or slide the selected set as the viewport moves. Install the selected covers before attaching or replacing a photo-bearing canvas. Subsequent scrolling moves those page-owned covers with their pixels, so the first visibility callback only evaluates entry eligibility and never races to hide an already revealed photograph. A region outside the current clip can remain queued for its own first eligible encounter.

A successful candidate can make one crop ready while unrelated photographs remain pending; a collage waits for the resources affecting its selected rectangle. A protected queued crop waits for source readiness, the existing entry/scroll-settle condition, or resources still owned by an admitted speaking cast. The finite cast wait uses its current speech/return owner and normal capacity notification, with no additional timer or raster reservation. Once these entry conditions hold, synchronously try to allocate its actor/cargo work from the existing limits. Success adopts the cover and starts one finite delivery. An actual capacity, route or copy-admission refusal marks the crop skipped and removes its cover in that same transaction, exposing the current successful pixels. A later capacity event cannot revive the skipped crop. Other still-unready crops continue to await their own source events.

The page presentation decision never waits for a promise or animation capacity. It prepares any new protection and immediate admissions, commits the native/preview raster synchronously, then finalizes the plan transition. A publication failure rolls back newly prepared work without changing the preceding displayed candidate or its owned covers. An uncovered publication records exposure before returning. Metadata that arrives after that point can help future source regions, but cannot retroactively mask already exposed or unknown regions. Missing metadata retains the completed-raster fallback only when that raster can still be protected before its first attachment; otherwise the encounter is skipped.

Queued covers advance on successful candidate publication, image-resource outcome, page/viewport geometry or the existing scroll-settle event. They run no animation loop and retain no raster. A failure that makes an uncovered dependency impossible skips the affected crop and reveals any useful partial pixels; a failed refinement with usable coverage need not cancel a valid crop. Effect disabling, reduced motion, document hiding, incompatible appearance, page removal and document replacement release queued covers immediately. Active work resolves or cancels through its existing finite owner. All terminal states and exposure decisions survive ordinary rerenders and geometry reconciliation.

Queued offscreen protection is bounded by the existing retained/prepared page sets. Eviction releases that page's covers and cargo while retaining every committed selection and its source-page history. A bounded selection can leave other photographs uncovered; a later clip or zoom cannot use eviction to select and conceal those photographs. Only an uncommitted provisional plan with no encounter, possible exposure or terminal crop may be discarded after all its presentation candidates detach. Releasing a cover while leaving its candidate connected records exposed/skipped state. Removal and incompatible appearance changes cancel remaining work while preserving the same source-page history. Only source-document replacement resets that history; an explicit resource retry cannot conceal pixels that the failed attempt already exposed.

Coverage is a discriminated value: known native object membership, verified complete-page coverage, or unknown coverage. Preserve that distinction through cache copying and resizing. ### Placement metadata and payload geometry

Placement metadata needs an explicit source-resource link for early individual-photo admission. The preview producer's `p{page}-i{ordinal}` identifies a placement; the reading producer's `x{xref}` identifies an original PDF image object. Preserve both identities. Add an optional `resourceId` to each image region, derived from that occurrence's actual original xref, and retain its existing normalized bounds. Repeated placements keep distinct region IDs even when their resource is shared. Export successful native coverage by registered object identity with its source resource ID. If several native instances use the same resource, resource-level readiness requires all relevant instances in that successful pass to be covered; one covered alias cannot stand for another missing placement. Native completion of a composed image includes its mask dependencies.

The producer also declares whether its occurrence inventory is complete after validation and region limits. A crop's requirements include all known image occurrences intersecting that rectangle, not only the named subject of the delivery. Incomplete inventories, inline images without a source-resource link and unsupported placements use the conservative complete-candidate path. Bounds are for projection and intersection; neither bounding-box coincidence nor an ordinal inferred from another renderer establishes resource identity. A decoded-image digest also cannot establish that link: distinct XObjects and inline images can contain identical pixels. The producer must validate the actual occurrence-to-resource relationship, leave unproven links absent and clear completeness when any occurrence remains unresolved.

This metadata extension is additive. The preview schema and consumer preserve validated optional resource links and completeness, and bind them to the same original document identity as the reading manifest. Unknown resource IDs cannot grant coverage. Existing manifests remain readable and their raster previews retain their current behavior; missing links disable early region admission without blocking PDF display or fabricating a mapping. A same-identity producer rerun upgrades legacy occurrence metadata once while reusing valid raster assets. A present conservative completeness result is already processed metadata, so unsupported pages do not regenerate on every run. The ordinary completed-raster fallback can choose work before its first presentation. If those pixels are already visible when metadata arrives, that work is skipped for the encounter. Regenerating metadata does not change the original PDF, download identity or already verified image bodies.

For already published Spomenar editions, `spomenar-watch.py` checks metadata freshness separately from full-atlas integrity. Once the full edition has its current reading representation, any page missing a boolean `imageRegionsComplete` schedules one ordinary metadata job. The watcher seeds or resumes its owned work directory from the verified public atlas, then uses the existing producer, publisher and atomic commit path. Existing verified tiers receive manifest-only metadata updates, preserving their exact descriptors and raster files; only missing tiers are rendered. Fresh raster generation finishes and closes its document before occurrence extraction opens a separate document. An explicit `false` counts as processed. Failure, cancellation or an incomplete producer result keeps the prior public atlas, PDF and reading identities usable; restart can resume the staged work. The successful commit updates the saved manifest revision and catalog, so the watcher does not mistake its own enrichment for an out-of-band replacement.

When matching placement metadata is available, couriers select actual image rectangles from the rendered page pixels and deposit them at those images' real locations. Normalized coordinates follow the page's intrinsic rotation and the viewer's additional rotation. Transport admission requires at least 32 CSS pixels of the selected rectangle to be visible in each dimension. The crop preserves the PDF's clipping and colour treatment. Candidate selection deduplicates the exact clipped source-pixel rectangle, including placement aliases and sampled fallback crops whose centers clamp to the same rectangle.

Each admitted payload is one page-region job with one crop, arrival cover, deadline and attached crew. The shared page-space planner rejects positive-area overlap with existing jobs before allocating a raster or reserving actors. It compares the final logical crop, allowing touching edges independently of raster rounding and cover padding. Whole photographs, collages and portions are chosen in content-priority order before ground routes are considered. A cooperative enlargement passes the same region check; other crews receive distinct work. Failed construction leaves no claim. Distinct placements of the same image remain separate jobs, and refinement joins the existing job without changing its region. Retirement uses the same rule separately for each old page, so its claims cannot suppress an incoming document.

The [document presentation policy](../views/pdf-viewer/src/common/robot-document-policy.ts) chooses cargo from its displayed CSS footprint. The maximum edge is 400 CSS pixels on desktop or 256 in compact presentation, multiplied by the bounded page-size factor described below. Viewport movement cannot slide a portion's boundaries. Payload snapshots identify the crop kind and its source image IDs; the admitted crop, helpers, identity and deadline remain fixed through sharper previews and native rendering. Revisiting or zooming does not replay terminal work.

Neighbours must form aligned rows or columns: their gutter is at most 8 CSS pixels and 6% of the smaller image edge, and their alignment differs by at most 2 CSS pixels and 2%. Geometry-only changes reconcile the same source page's normalized target and projection while preserving its delivery identity and deadline. A terminal crop or replacement document cannot restore a cover. If protection was lost while a candidate remained exposable, the plan records a terminal outcome instead of concealing those pixels again. At least one dimension must grow, or the source must carry a newer painted content revision at the same dimensions. Old and new rasters must fit the cargo budget together during replacement.

| Preview source | `previewSource` exposes source state, manifest and asset request counts, available page coverage, pending work and decode activity. Sidecar events enter the same bounded performance event buffer. |
| Transfer pressure | `fetchBackpressure` reports the request-admission condition. The performance snapshot includes `pendingFetchCount` and `oldestFetchMs`. |
| Device retention | `cachePolicy` and `cacheLimits` expose the selected device budget. `rangeCache` reports worker residency, eviction and peak byte counts. `memoryBackpressure` explains when new cold work is waiting for cleanup. Results from replaced documents are discarded. |
| Decoded images | `decodedImages` counts retained image backing buffers and estimates bitmap storage as width × height × four bytes. Shared objects and aliased buffers are counted once, with shared storage attributed first. The scan is bounded to 512 page views and 512 stored objects; unsupported or incomplete results are labeled. These readings are separate from raw PDF bytes, preview rasters, native canvases, and total browser memory. |
| Image decoding | The worker statistics include current and peak active image jobs, queued jobs, completed native and fallback decodes, and cumulative original/output pixel counts. They use the existing byte-statistics request and stop with its lifecycle. Pixel totals describe decoded work; retained memory is reported separately by `decodedImages`. |
| Document fleet paint | The measurements panel reports the document renderer's last, mean and maximum paint duration, paint count and active actors. `robots.paintLastMs`, `paintTotalMs`, `paintMaxMs` and `frames` supply these values. These measurements cover document couriers; the optional lab canvas has its own renderer counters. No additional sampling timer is created. |
| Cargo admission | `robots.operationAdmissions` counts cargo admission calls, `operationCandidates` counts assessed proposals and `operationCommitChecks` counts their commitment checks. `operationAdmissionTotalMs` and `operationAdmissionMaxMs` include candidate assessment, reservations and the cargo copy. They measure the whole admission operation separately from painting. |
| Operation decisions and state | `operationNarrativeRecords` counts canonical decision records created since the document was reset; `operationDecisionRecords` reports the currently retained count. Each payload's `operation` snapshot exposes its admitted members, phase assessment, stable decision, outcome, timing, current activity phase and resolution. Refinement advances presentation while preserving those committed choices. |
| Lab raster backing | `labRobots.renderer.raster` reports the main backing width and height, cached-body dimensions, density, jointly owned bytes, byte budget, limit status and resize count. The dimensions and owned byte count return to zero on disposal. |
| Disk accumulation | `performance.diskCache` reports this build's stored/total bytes, all builds' disk usage and budget, and whether filling is active, paused or complete. Host updates are coalesced to at most one per second. |
| Idle fill eligibility | `idle` becomes true only with a covered viewport, no motion, no cold-page jobs, no foreground fetches, no active native render and no unsettled worker-byte operations or memory pressure. Both extension engines send this state with their page ID and displayed build ID. Motion, fetch admission, rendering, hiding and disposal revoke it immediately. |
| Visible-content status | `visibleMissing` lists visible pages awaiting both a full render and a preview; `starved` is true when that list is nonempty. |

The time margin extrapolates the present speed and recent loading cost. Abrupt jumps and changes in page complexity change those estimates.

### Activating an installed viewer

`./scripts/install-local-build.sh` installs the checkout's frontend bundles into the matching local extension. Before recreating an existing Antigravity reader, capture the document identity, page, zoom, rotation, spread and scroll modes, exact scroll offsets, sidebar, Motion Lab state, editor groups, split widths, tab preview/sticky state and focus. Restore those captured values after the new reader loads, with trusted user input taking priority.

For the existing two-group layout with a clean, kept source tab on the left and a clean, kept PDF tab on the right, keep the right group alive during recreation to preserve its width:

1. Use `View: Focus First Editor Group` and verify that the source tab is the active editor in the active group.
2. Use `View: Split Editor into Right Group`. This copies the source into the existing right group as a temporary second tab. Verify that both original groups and the PDF tab remain present.
3. Close only the clean PDF tab and use `View: Reopen Closed Editor`. Wait for the replacement reader's document and service worker to become ready.
4. Focus the right group with `View: Focus Last Editor Group`. If needed, use `View: Open Next Editor in Group` to select the temporary source tab; verify that selection before using `View: Move Editor into Left Group`. Moving the duplicate back merges it with the existing source tab and leaves the right group containing the PDF.
5. Restore the captured reader, panel and focus state. Verify both group widths, the exact tabs and active group, and the reader state after the final focus action.

Use the workbench's group and editor commands for automated selection. A synthetic click on an already selected tab did not activate its group in the live check, so the following split acted on the PDF instead. The explicit commands and active-state checks preserved the measured 468.997 / 1266.992-pixel split. Copy, reopen and move keep editors open; automation should verify already-kept, non-sticky tabs before this sequence. Reserve time for recovery, reconcile the actual tabs after an interrupted command, and keep input and document-identity guards attached through restoration and cleanup.

The observed reload left the replacement content without service-worker control and its extension-resource requests failed. Normal close and reopen recovered controlled resources and loaded the installed bundle.
